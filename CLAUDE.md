# CLAUDE.md

File guides Claude Code (claude.ai/code) working in repo.

## Project

Mobile-first golf game. Vanilla JS + HTML5 Canvas. No build step — open `index.html` direct or serve with Python.

## Running locally

```sh
cd ~/Documents/GitHub/golf-game
python3 -m http.server 8080
```

Desktop: `http://localhost:8080`  
Phone (same WiFi): `http://<your-mac-ip>:8080`

**Admin server (optional):** `python3 tools/bake_server.py` — drop-in replacement for `http.server`, ALSO exposes `/api/search` + `/api/bake`. Powers in-game admin **➕ Add course** button (search course → bake via `fetch_course_global.py` → append `courses/manifest.json` → git commit). Flags: `--port 8080 --no-git --push`. Button admin-gated AND hidden unless `/api/ping` answers — plain static deploy never show it. Course list from `courses/manifest.json` (fallback: hardcoded `FALLBACK_COURSES` in game.js).

## Concurrent Claude Code agents

Many agents can work repo at once. Two independent isolations — **neither need commit or push**:

- **Browser (Playwright):** `.mcp.json` runs Playwright MCP with `--isolated` — each Claude session get own ephemeral Chrome profile, no fight over shared profile dir (`mcp-chrome-*`). Without it, second agent hit `Browser is already in use ... use --isolated`. Isolated mode keep no persistent browser state — fine here (localhost, no logins). Dev server (`python3 -m http.server 8080`) shared; one instance serve all agents.
- **Files (git):** stop agents clobbering edits — give each own **git worktree** (`git worktree add ../golf-game-<name>`, or Agent tool `isolation: "worktree"`). Each worktree = separate working copy, own branch; merge when done. Commit/push only for sharing results, never prerequisite for parallel agents.

## Coordinate system

Per-hole world bounds (`WORLD.w/h`, set by `setHole`); origin top-left, tee bottom, pin near top. Scale **fixed** at `YARDS_PER_UNIT` (≈3 yds/unit, from course JSON) — given swing = same distance every hole. `view.scale`, `view.ox`, `view.oy` map world→screen via camera rect; `wx(x)`, `wy(y)`, `ws(v)` convert coords/sizes. Recomputed every window resize + hole change.

## Camera framing + HUD bands

**`hudReserve()` is MEASURED on mobile, not constant.** `HUD_RESERVE` is a floor; `measureHudBands()` (next to `hudReserve`) caches `#scorecard`'s real `bottom` and `hudReserve()` returns `max(constant, measured)`. The mobile top bar is a full-width card whose height moves with CONTENT — 79.5px solo, **94.5px in a match** (the "Match: 2 UP" line) vs the hardcoded 78 — so the fixed value under-reserved exactly when the bar was tallest and the framed landing area got painted over. Re-measured by a `ResizeObserver` on `#scorecard` (+ `resize()`), never inside `hudReserve()` — that runs several times a frame (`frameScaleForAngle`, `frameClubReach`, `computeViewMatrix`, `visibleRect`, `paintGreen3D`, the 3D bridge) and per-call layout reads would thrash. **Measure only bands that span the WIDTH:** the club wheel is a 96px dial in the bottom-RIGHT corner, and measuring it reserved 182px instead of the tuned 124, cutting 9% off the play area and pulling the camera IN — shrinking the very span the fix exists to reveal. Bottom stays constant; desktop stays constant entirely (its bar is a top-LEFT panel, not a band).

**gtiles framing budget is camera ALTITUDE, not shot span** (`three3d/gtiles3d.js` `setCamera`). Was `SPAN_MAX_U = 70` framing 70u while a driver reaches ~99u; at low pitch screen-y is linear in ground distance, so the landing point projected to y ≈ −8..+11 on an 844px screen. Measured across all 18 Pebble holes at 390×844: **pitch 0 hid the landing spot on 14 of 18 holes; pitch 55 hid only h18, by 4px** (perspective already reveals ground beyond the reach anchor once the camera leans). So the clamp is now **pitch-dependent** — 70u at pitch ≥ `SPREAD_PITCH` (45), lifted as the camera flattens — plus `D_MAX_M = 820` as the real cap. Anchor fractions are pitch-dependent too (`REACH_F/BALL_F` 0.18/0.88 high, 0.07/0.93 at pitch 0): spreading them buys span for FREE, so spend that before altitude. Result 36/36 clear, min clearance 13px solo / 96px in a match; `D` pitch-0 675→777, **pitch-55 356→369** (removing the clamp at every pitch pushed pitch-55 to 503m, past the ~413m where the note in the file records the mesh crawling in — don't do that). When `D` hits the cap the look-at is anchored off the **BALL** (`sB`), not the reach point: solving from the reach end slides the frame forward and drops the ball off the bottom.

**Off-screen widen guards measure the PLAY BAND, not the raw screen** (`gtiles3d.js` guard + `updateCamera`'s flat-path guard). The mobile bar covers ~9.5% of the height, so a ball resting at screen `yf` 0.08 was fully hidden yet read as safely inside the old 0.05 raw band and never widened.

**BALL FLIGHT IS NOT ALLOWED TO DEPEND ON THE CAMERA (2026-08-03).** On the photoreal ground the drawn ball is not its physics position: `project()` places it at `terrainZRender + offsetAt(x,y)`, and `offsetAt` is fed by `meshHeightAt` raycasts against **whatever tile LOD is currently loaded**. That closed a loop — the mid-flight widen moved the camera → `camMoved` raised `errorTarget` 6→12 → coarse tiles swapped in → the raycast returned a different surface → the ball's drawn height moved. Physics never touched any of it, which is exactly why it read as "the trajectory changes when the camera moves". Measured at HEAD on a Pebble drive: the ball's mesh offset moved **3.6 m (h1) / 4.0 m (h18)** in flight, the camera took 6–17 distinct positions, and **a stationary world point wandered 5–79 screen px**. Now 0 m / 1 position / **0 px**. Three parts, all load-bearing:
- **The camera is LATCHED for the whole shot** (`_shotCam` in `setCamera`). Captured *after* the first moving frame places the camera, so the freeze is literally the frame the shot started on and can never introduce a step of its own; released at rest, seeding `_camEase`/`_groundMEase` from the latched values so the return is a glide. `_guardK`'s `off && S.moving` arm is GONE — that per-frame 1.04^n widen (capped 2.5×) was the head of the chain. Its at-rest `_guardLostN >= 5` arm stays; it recovers a framing that lost the ball while the height field healed, and it can no longer run during a shot.
- **The whole shot is pre-framed at ADDRESS** — `frameAnchors()` returns a third anchor `ax/ay/az` (club `maxH` × `TUNE.frameApexK` × the partial-swing shrink, at `TUNE.frameApexFrac` along the aim; `az = 0` on the green keeps putt framing byte-identical, measured `D` 57 → 57), and `setCamera` grows `D` 1.08× at a time until the crest clears the `REACH_F` line. Four details are not optional: the fit runs **before** the flat-reference blend so pitch 0 stays the flat 2D camera by construction; the ball is re-pinned at `BALL_F` at each step (growing `D` alone drags the ball toward screen centre and leaves dead space under it); the crest is projected at `terrainZRender(x,y) + z`, since passing `az` alone puts it on the datum and reads metres low uphill; and it samples **three** fractions across the crest — on sloped ground the highest point on screen is not at a fixed fraction, and one sample left the ball cresting out of frame (h6 `yf −0.137`, now +0.022 with all 18 holes positive). Each sample carries a parabolic height normalised to 1 at `frameApexFrac`, NOT the flat apex: holding `az` across the spread framed apex height at 0.70 of the carry, where a real ball is already descending, and cost `D` an extra 1.08 step on 3 holes.
  **Measured cost, and it is not small.** Pitch-55 driver `D` **369 → 465-542 m** (most holes 502), 7i 327 → 381. `D_MAX_HI` 820 still caps it, but this is past the ~413 m that the note above records as where the photoreal mesh starts crawling in — the tee on a driver hole streams in visibly slower. Deliberate trade, chosen over a camera that moves. Part of the increase is not optional: at `D` 369 the ground REACH anchor itself projected ABOVE the play band on **6 of 18 holes** with a driver (h11 `yf −0.042`, h13 −0.038, h4 −0.014), i.e. the landing spot was already off-screen at address and the mid-flight widen was covering for it. Knobs, cheapest first: `frameApexK` (1.10), the fit's `yLimit` (currently the `REACH_F` line — the ball's true crest lands ~0.13 of the band above wherever the estimate is placed, so this cannot go much below 0.16), then `frameApexFrac`.
- **The mesh-height field is frozen while the ball moves** (`_fieldFrozen = _camParked || moving`), gating the `_fro` snapshot, `_groundMEase` and the per-green `rec.disp`. `refreshGridBatch`/`refreshPrecisionAnchors` are skipped outright during a shot — their output is discarded anyway, and it drops ~26 BVH-less full-scene raycasts per frame exactly when the budget matters. The ball anchor's own ±8 m sanity guard was **inert in flight** (it requires the ball to have moved < 5 units, never true mid-flight), which is why the freeze and not a tighter guard is the fix. At the rest edge `_ballOff` (rendered) eases toward `_ballTgt` (raw) over ~250 ms and a NEW column seeds from `_offsetBase` — the ball spent the flight drawn against the coarse grid, so adopting the exact anchor outright steps the ground under it by the 1–2 m the anchor exists to correct. First anchor of a hole still snaps (nothing rendered yet, and an unfilled grid would start it ~40 m out).

Gate it with `cd web && node scripts/flight_probe.mjs` (all 18 Pebble holes; needs a Map Tiles key). The load-bearing assertion is the **witness**: a fixed world point projected every frame must land on the same pixel. Everything else (offset spread, `errorTarget`, camera position, `camSeq`) is a symptom of that one invariant. `maxJerkPxPerU` is printed but NOT gated — with the witness at 0 the screen path is a fixed projection of the physics arc, so any jerk left belongs to the physics (a `clampToWorld` bounce, a hazard reset), and gating it makes the probe police the ball flight. Two traps when editing the probe: `state`/`ballTrail`/`selectedClub` are script-scope `let`, NOT on `window` (reading `window.state` silently returns undefined and the probe "measures" a shot that never fired), and the shot must fire from a **settled** scene or the pre-shot `errorTarget` ramp reads as churn the shot caused. `scripts/framing_probe.mjs` reports the `D`/anchor cost of the apex fit; it must wait for the camera position to go quiet, not for `isSettled()`, which is still true for the first frames after a club change.

**The ball trail is in WORLD coordinates** (`ballTrail`, `sampleBallTrail`, `trailGen` in game.js). It stored baked screen px, so any camera motion between two samples left retained points at stale screen positions and the tail kinked and lagged. Points are now `{x,y,z}` pushed from the PHYSICS step (not `draw()`, which tied point spacing to the paint rate and thinned the tail exactly when the frame rate dropped) and projected at draw time through the same `wx`/`wyg`/`ballLiftPx` the live ball uses, cached per entry against `trailGen()` — `GTiles3D.camSeq()` on the photoreal ground (frozen for a shot ⇒ the tail projects once per flight), the affine's own six coefficients plus the terrain-lift terms on the flat camera. Fixes the flat 2D tail too, which smeared under `updateCamera`'s own widen guard. The clear stays in `draw()` because `update()` early-returns at rest and in the hole.

**The launch HEADING is forward-projected, never raycast** (`swipeToShot`'s `gtilesProj` branch). It used to `unproject()` two screen points against the tile mesh, so the shot direction — a physics input — depended on which tiles had streamed, and a missed ray fell through **silently** to the flat-affine formula, a different answer. Now three `project()` calls at the ball give the local screen←world Jacobian, inverted to turn the swipe into a world direction. The (right, up) pair only names the basis the Jacobian is measured in and is rotated back out of, so the result does not depend on it matching the tiles camera's exact bearing; verified algebraically identical to the flat formula under a top-down affine. `offsetAt` cancels because all three probes sit within a unit of the ball at the same ground reference.

**Match camera holds on the tee until both players are away** — `cameraTeeHold()` / `bothTeedOff()` / `oppTeedOff()` next to `myTurn()`. Two people share a tee box, so reframing after the first drive yanks the view off the player who hasn't hit. Gates `liveCameraTick`'s opponent follow, the at-rest reframe in `rollStep`, and (via `frameAnchors().hold` → `A.hold` in `setCamera`'s freeze test) the 3D camera, which otherwise re-captures `_hold` from the ball every at-rest frame and drifts anyway. The opponent's ball still DRAWS while held (`oppGhostPos` feeds the renderer independently of the camera). Two load-bearing details: `oppTeedOff()` must accept `cur_at_rest === false` because the bot only increments `cur_strokes` when its flight RESOLVES (`cpuDriverTick`), so mid-tee-shot it still reads 0; and `oppResponsive()` is in the condition so an opponent who never tees off can't leave you staring at the tee unable to see your own ball.

**Known latent (NOT fixed):** `gtiles3d.js` measures `window.innerWidth/innerHeight` in ~9 places (`project`, `pxPerMeterAt`, `unproject`, `setCamera`, camera aspect, `resize`) while `hudReserve()` returns css px sized to the `#game` canvas box (`vpH()`). `game.js` deliberately abandoned `inner*` so "nothing can tear against the CSS box"; where the two differ (mobile Safari dynamic toolbar) the reserve is applied against the wrong height and the WebGL buffer stretches against `#cgt`'s CSS box. Left alone because `innerHeight === vpH()` in headless Chrome and the Capacitor webview, so the change is unverifiable on the rigs available — don't "fix" it without a device that reproduces the difference.

## Course data pipeline (Phase 2)

Real geometry from OpenStreetMap via Overpass API (`golf=green|fairway|tee|bunker|water_hazard|hole`). Strategy: **pre-bake, not live-fetch** — `tools/fetch_course.py` query one course (by boundary way id), project lat/lon → per-hole world units (tee→pin oriented "up", fixed yards/unit), write normalized `courses/<id>.json` game fetch statically.

Geometry **real-first**: greens, bunkers, water, tees, **fairways**, **rough** (`golf=rough`), plus **woods/cartpaths/grass** from real OSM polygons (`golf=*`, `natural=wood|water`, `landuse=grass`). Hole lines ordered by leading int in `ref` (handles `"7"` and `"7 - #2"`), deduped by number. Fairways/bunkers/rough/woods/cartpaths/grass assigned to **nearest hole** (centroid→centerline). Fairway corridor **synthesized only as fallback** for holes with no mapped fairway (links courses like St Andrews) — tool print how many holes fell back.

**Rough vs fairway inference:** `surfaceAt()` return `"rough"` as implicit default (any point not in water/bunker/green/fairway/tee/woods polygon); mapped `golf=rough` now also baked as explicit `rough` surface (mostly aid rendering — physics already default rough). Real accuracy fix = **aerial-carved fairways**: holes with no OSM fairway, bake replace crude fixed-width corridor with **variable-width ribbon measured from Esri aerial** (`measure_fairway_ribbon`/`carve_synth_fairway` in `fetch_course.py`; `carve_synth_fairways` in global tool). Classify mown fairway grass by HSV (`is_fairway_px`, `FW_*` constants — may need per-course tuning), march perpendiculars off tee→pin centerline find each edge, **clamp width ≤ fixed corridor** so world bounds stay valid. Need **Pillow** (optional — `try: from PIL import Image`); without it, or classify fail, fall back to fixed corridor (e.g. Pinehurst sandy no-rough holes no carve, keep rectangle).

**Aerial imagery:** tool also bake one north-up **Esri World Imagery** JPG per hole into `courses/img/<id>/hole<N>.jpg` (keyless), plus pixel→world affine `aerial.toWorld=[a,b,c,d,e,f]` (`world.x=a*px+b*py+c`, `world.y=d*px+e*py+f`). Game draw photo as hole base, rotated to play "up" via affine — no image processing for *rendering* (Pillow not required there). `--no-imagery` skip. Pillow **is** used (optional) to carve synth fairways from baked aerial — see "Rough vs fairway inference" above.

**Imagery source (Esri vs NAIP — monetization gate):** Esri World Imagery free ONLY non-revenue — terms forbid monetized apps (ads/subscriptions). So `fetch_course.py` expose `IMAGERY = {esri, naip}`, both bake tools take `--imagery {esri,naip}` (default `esri`). **NAIP** (USDA National Agriculture Imagery Program, via The National Map `USGSNAIPImagery/ImageServer/exportImage`) = **public domain, commercial-OK, keyless, US-only**, identical ArcGIS export API — license-clean swap. Baked `aerial.src` field record `"esri"|"naip"`; game on-map credit (`drawAttribution` in game.js) read it → "Imagery: USGS / NAIP" vs "Imagery © Esri" (+ always "© OpenStreetMap contributors" for OSM-derived courses; Originals skip OSM line). **`tools/rebake_naip.py`** batch-swap every US (`region:"USA"`) course to NAIP in place (resumable — skip `aerial.src=="naip"`; git-restorable; boundary ids from `courses/index.json` + `OVERRIDES` map for hand-baked): `python3 tools/rebake_naip.py [--dry-run|--only a,b|--limit N|--force]`. **Aerial surface mask (OOB + fairway/rough from what you SEE):** OSM polygons make OOB inconsistent (only `natural=wood` counted — neighborhoods/roads/parking defaulted playable rough), fairway/rough coarse. So bake also classify aerial per-pixel into coarse **label raster** (`courses/img/<id>/surfacemask.png`, palette `OB=0 / FAIRWAY=1 / ROUGH=2 / WOODS=3`) + `surfaceMask:{file,w,h,toWorld}` affine. `build_surface_mask`/`_classify_px` in `fetch_course.py` (wired into `fetch_course_global.py` after aerial download): green-turf by HSV (reuse `is_fairway_px` band); fairway-vs-rough by **brightness split** (Otsu over green pixels → `_otsu`, mostly kill per-course tuning); woods = dark + high local edge energy (`FIND_EDGES`+`BoxBlur`); everything non-green = **OOB only outside playing envelope** — inside it, non-turf (sand/path/dirt) just rough, so fairway bunker not mistaken for parking lot. Envelope = **union** of OSM boundary polygon, buffered hole centerlines (`MASK_CORRIDOR_UNITS`), OSM play polygons (fairway/green/tee/bunker), all dilated outward by `MASK_ENV_DILATE_UNITS` — parcel lines often cut through real dunes/fairway edges (coastal + multi-parcel courses). Outside envelope, **sand-looking pixels rescued to rough** (bright/warm/low-sat, `MASK_SAND_*`) within `MASK_SAND_NEAR_UNITS` of it — sand never OB. Despeckled (`ModeFilter`), OSM `woods` unioned in as strong prior. **Shadow-streak guards** (tree shadows across fairways on leafless/low-sun aerials classify as woods = phantom mid-fairway penalty): heuristic WOODS demoted to ROUGH within `MASK_WOODS_CORRIDOR_UNITS` of hole centerline and within `MASK_WOODS_FW_HALO_UNITS` of mapped fairway (OSM-mapped woods repainted after — real dogleg forest survive), mapped OSM fairway polygons pasted in as FAIRWAY ground truth last. Tunables: `MASK_*` constants. Pillow-optional + guarded (no Pillow / classify fail → no `surfaceMask` key). `--no-mask` skip. **Game side:** `loadSurfaceMask`/`maskClassAt` (game.js) decode PNG once (nearest-palette → `Uint8` labels), sample in `surfaceAt()` — OSM stay authoritative for green/bunker/water/tee, then **mask decide OB vs playable** (envelope already fold in boundary polygon; fairway/rough/woods/`ob`), then vector `boundary` polygon (OB outside it, except mapped fairway) cover off-mask points, then OSM polygons on no-mask holes. `tools/remask_courses.py` rebuild every course mask offline from baked aerial + JSON (no Overpass); `--audit` print OB-in-fairway / OB-near-centerline metrics. ## Key tunables (`TUNE` in game.js)

| Constant | Effect |
|---|---|
| `powerFactor` / `maxPower` | Swipe speed → launch speed; derived from `YARDS.maxCarry` projectile range |
| `launchAngleDeg` / `gravity` / `airDrag` | Ball-flight arc shape + hang time |
| `spinFactor` | How hard curved swipe bend flight (draw/fade) |
| `bounce.<surface>.{e,h}` | Landing: `e` vertical restitution, `h` horizontal speed retained |
| `bounceStopVz` | Downward speed below which bounce stop → rolling |
| `captureSpeed` / `captureAssist` / `HOLE_RADIUS_UNITS` | Cup forgiveness. A real ball is captured dead-centre only below `d·√(g/2r)` = **1.64 m/s** (it must fall about its own radius while crossing the cup). `captureAssist` was 0.08 = 3.51 m/s, **2.15× that ceiling**, now **0.062** (1.66×) — it was the most unphysical number on the putting path. `captureSpeed` and `HOLE_RADIUS_UNITS` are deliberately UNCHANGED. **Do not "fix" the cup to real size**, and read this before trying: it is 0.055 u = 11.9 in vs a real 4.25 in (2.80×), which looks indefensible until you measure outcomes. There is no read or aim aid, and swipe aim resolves to ~±1° — at 5 ft that is ±1.05″ against only 1.28″ of real margin. Measured blind-aim make rates already sit at tour difficulty where the comparison is valid (3 ft 94%, 5 ft 75% vs tour 99/77 **with** a read). Cutting it to 0.046 was tried and reverted: 5 ft fell to **64%**, below tour, while the lag putts it was meant to correct moved only 2–3 points. The long-range comparison that motivated it is invalid anyway — at 20–45 ft the break is 2.6–6.2 ft against a 0.5 ft cup radius, so blind-aim makes come from the flat-spot tail of the sampling, not from a read. The lag rates came down on their own (30 ft 15→12%, 45 ft 12→8%) from `gMicroGrade` + the `captureAssist` cut, with short putts held (3 ft 92%, 5 ft 73%) |
| `puttTimeScale` | Wall-clock pace for a stroke played FROM the green, same idea and same value (2.0) as `chipTimeScale`. A 20 ft stimp-11 putt rolls **4.94 s** in life and took **1.32 s** at a flat 3.75 — the one shot in golf watched in real time, played as a flick; 2.5 s now. Free in accuracy: the pace is set in `launchShot` BEFORE `buildTrialShot`, so `invertPuttPaceCurved` solves at the dt the live steps then integrate at. Gated on **`onGreen`**, not on "putter selected". That gate WAS load-bearing (the off-green stroke's `puttOffGreenPower` ceiling is frame-dimensioned and derived at `timeScale`); since that ceiling was removed the off-green putter is free to take `puttTimeScale` too, and stays at `timeScale` purely as a feel choice. For the same reason `recalcPower()` now derives `puttMaxPower` with `simScale` forced to default: holing out leaves `simScale` at `puttTimeScale` and `setHole` recalcs immediately after |
| `friction.*` | Per-surface rolling velocity multiplier per frame (fairway/rough/bunker/water; lower = more friction). Green separate (constant deceleration, see below) |
| `greenDecel` | Green roll: constant deceleration/frame, derived from stimp (`GREEN_DECEL_K / greenSpeed`); realistic putt rollout |

## Ball flight & physics

Swing = **putt** (on green: stay grounded, roll with slope-aware break — see Topographic green) or **full shot** (airborne projectile). A putt leaves the face **ROLLING** (`startRollingSpin` sets `w = v/r` — live launch, `simShotRest`'s copy inherits it, `invertPuttPaceCurved`'s forward roll re-derives it): without it the ball entered `skidRoll` fully slipping and burned a whole tick on kinetic friction (green `mu`·g ≈ 7 m/s² over a 62 ms tick), so pace had to launch 35% hot — a 20 ft putt at 3.32 m/s where the stimpmeter says 2.47, with `shot.mph` showing the hot number. Dead pace is inverted on the ball's **straight-line displacement**, not arc length (`invertPuttPaceCurved`): on a 3% cross slope a putt covers 20 ft of arc but finishes 19.5 ft from the start, so an arc-length target dies short of the cup by 2.6% (5.4% at 4%). State carry `z` (height), `vz` (vertical velocity), `spin`. `update()` dispatch to `flightStep` (gravity arc + sidespin curve + land/bounce) or `rollStep` (per-surface friction + hole capture + water). Each club carries its own rated distance from `TUNE.clubs` (`YARDS.maxCarry` is inert); bounce + rollout add more. Shot shape from swipe curvature (`curveFromPath`). Rendered with ground shadow at `(x,y)`, ball lifted by `z`.

**One ground-roll step (`stepGroundRoll(b, surf)`).** Velocity-only, dispatched by surface; callers own position, clamping and the cup. It existed inline in THREE places — `rollStep`, `simShotRest` and (wrongly) `invertPuttPaceCurved`, whose forward roll called `stepGreenRoll` **unconditionally**. So any predicted path that ran off the green kept decelerating at green stimp and the putt was paced for a green that wasn't there: measured worst-case pace error **5.79 ft on pinehurst and 27.77 ft on harbour town**, against a 0.00 ft median, entirely on the putts that finished off the green. Never re-inline it — the whole failure mode is the prediction and the live roll disagreeing about what the ball is rolling on.

Two things that inner loop must keep doing: (1) **read the surface EVERY step** — sampling it once on green-exit and reusing it looks like a safe optimisation and is not. (2) **call `clampToWorld`**, exactly as `rollStep` does, or a predicted path runs past a world edge the live ball bounces off.

**Known residual, and do not "fix" it by loosening the gate.** Making the roll surface-aware costs the solver its monotonicity assumption. `invertPuttPaceCurved` bisects on displacement-vs-launch-speed, which is monotone on a green (as its comment says) but NOT across mixed terrain: more speed can carry the ball into heavier stuff and stop it *sooner*, so the bisection can settle on the wrong root. Harbour town shows exactly one instance out of 894 putts — hole 12, 45 ft, aim 5.50 rad, which points OFF the green, so the solver correctly asks for **28 mph** (a 45-footer needs 8.3; on pure green 28 mph would roll 512 ft) and lands 1.55 ft off. It trips `pace error max <= 0.60`. That is a blind-compass sampling artifact, not a gameplay case — no player putts 45 ft across rough on purpose — and it replaced a **27.77 ft** error at the same spot. Two dead ends already explored, so don't repeat them: it is not a lip-out and not a cup ram (`_lippedThisShot` is false, and the ball passes 1.65 ft wide of a 0.57 ft capture radius), and adding bisection steps will not help a non-monotone root. Diagnostic: `--json` the course, filter non-holed `D_ft > 6` resting on green, sort by `|disp_ft − D_ft|`. A healthy course is 0.00 ft for essentially every row (pinehurst and blackwater both max 0.01 ft), so one outlier is real; `mph` identifies this class instantly — wildly above `√(2aD)` means the aim leaves the green.

Because that prediction is now surface-aware, the **off-green putter (bump-and-run) solves through the same `invertPuttPaceCurved`** the green does. It used to be an uninverted `puttOffGreenPower · puttSensitivity · √f` ramp, so stepping one inch off the fringe silently changed what a swipe meant. No `TUNE.lie` multiplier on that branch: the lie's cost is already physical in the solved pace (rough decelerates several times faster than green), and re-applying it would charge for the same rough twice. The driving range keeps the old ramp — no pin to solve to.

**And no second CEILING on the solved pace** (2026-08-03). `TUNE.puttOffGreenPower` = `(30/YARDS_PER_UNIT)·(1 − friction.fairway)` is the closed form of the RETIRED per-frame exponential roll and was never re-derived for constant deceleration. 0.195 u/frame reads as 8.56 m/s, which is 7.2 yd of fairway, 4.4 of rough — and **80 yd of stimp-11 green**. So it was wrong in both directions at once: used as the POWER (shipped build) a half swipe from the fringe launched ~6 m/s and ran **40 yd**; used as a `Math.min` CEILING it saturated, and a measured 20 yd bump-and-run stopped at **4.8 yd (−76%)** with every swipe strength producing the identical stroke. There is already a cap on the only thing that should be capped — `targetU = min(flatU·band, YARDS.maxPutt)`, same as the green branch. The accepted trade: a long bump through rough now asks for a launch speed a real putter could not make. `puttOffGreenPower` survives only for the driving range, and `swingTimeScale`'s off-green pin to `TUNE.timeScale` is now a feel choice, not a correctness constraint (nothing on that path is frame-dimensioned any more).

**Both inversions return the BEST measured probe, not the final interval midpoint** (`invertPuttPaceCurved`, `solveChipEf`). Neither objective is smooth: displacement jumps when the roll crosses a surface seam a tick earlier (rough decelerates 18× faster than a stimp-11 green), and chip rest distance jumps because `buildFlight` quantizes the carry target to whole frames (`landD = ceil(C/vh0)·vh0`, ~7% at chip `ef`). Bisection converges onto the step EDGE and the midpoint then lands on an arbitrary side of the jump — measured ±15% on bump-and-runs that started in rough and finished on the green, and ±10% on chips, while putts that never left the green solved exactly. Keeping the best root costs nothing (the rolls were already paid for) and took on-green pace error to **0.00 ft median AND max**.

Lip-out: rolling ball entering `holeRadius` at speed ≥ `captureSpeed` reflect off rim (0.5 restitution); slow enough → sink (airborne balls can't drop). Water: ball land/stop in water → +1 penalty, reset to `state.lastSafe`. Per-surface `bounce` values = placeholders for real per-course data from future golf API.

**Holding greens (LIVE, `aeroPhysics`):** touchdown run `Ballistics.bounce` (normal impulse + Coulomb tangential impulse fighting contact-point slip + `dig` crater absorption), then re-fly if the rebound clears `aeroSettleVz`, else hand the ball's ANGULAR velocity to the roll phase (`aeroToRoll` → `b.spinW`) where `Ballistics.skidRoll` grinds the slip out. Check, hop and spin-back all fall out of that — nothing is scripted. Tuned by `TUNE.turf.<surface>`; measure with `node tools/shot_matrix.mjs`.

**Aero coefficients (`ballistics.js` `COEF`):** lift is `Cl = clMax·(1 − e^(−clK·S))` — SATURATING in spin ratio `S`, the shape a dimpled sphere actually measures. It replaced a power law `clK·S^clP` that returned Cl ≈ 0.17 at a driver's S ≈ 0.07 against a measured ≈ 0.11; fed the real TrackMan launch numbers that law flew every iron ~16 yd long and flat, which forced `aeroSpeedForCarry` to hold ball speed DOWN and land mid-irons 5–10° too shallow. Drag is `Cd = cd0 + cdS·S + cdRe·max(0, 1 − v/cdVRef)` — the `cdRe` Reynolds term is what lets one fit serve a 76 m/s driver AND a 36 m/s wedge; without it the model cannot be right at both ends of the bag. Club table `carry`/`ball` are now true TrackMan averages (the bag was uniformly +4..+7 hot, and 3w's 169 mph was a typo — 162). Re-fit with `node tools/ball_calibrate.mjs --fit` (~7 min, multi-start). **Known residual:** descent spans 44–54° vs a tour 39–55°; 6i and down land within ~1°, long irons 3–4° shallow, driver ~6° STEEP (45 vs 39) so drives run less than they should. Needs a Reynolds-dependent `Cl`, not another knob — see the header note in `ball_calibrate.mjs`.

**Short chips used to have a hard ~14.5 yd FLOOR** (fixed 2026-08-03). `aeroSpeedForCarry` bisected ball speed over `lo = 20, hi = 240` mph and bracket-checked only the HIGH end. 20 mph carries **8.1 yd at 35° and 8.4 at 45°** — longer than an entire greenside chip — so every request under that returned the floor, flew the same 8.4 yd and released: measured, an 8 yd chip finished **17–19 yd** from the ball (+115%/+133%). `solveChipEf` then hid it, because its own `lo = 0.02` was never probed either: when even the floor overshoots, all 14 iterations take `hi = mid`, the interval collapses onto `lo`, and it returns ~0.02 as if converged. Fix is symmetry — `lo = 4` mph (0.35 yd of carry) with a low-end bracket check in both solvers, plus `solveChipEf`'s `lo` scaled to the ask (`min(0.02, carryEf·0.25)`) so a big club can still be asked for a small shot. A `null` probe inside the loop is now treated as an UPPER bound (`hi = mid`) rather than a bail to `carryEf`: null means the ball died in water/OB/woods, i.e. it went too far, and bailing to a pure CARRY estimate is what made a chip over a hazard-backed green blow the pin by 30–50%, intermittently, depending on what was behind it. Measured after: LW 3→3.0, 5→5.3, 8→7.6, 10→10.4 yd; live engine 8 yd chip +115% → −2.0%. `shot_matrix`'s `CHIP_TARGETS` gains 3/5/8/10 and its rest tolerance goes relative at the short end (20% or 1.5 yd) — a flat ±2.2 yd passes a 3 yd chip that finishes 5.2 yd out.

**Pitch trajectory:** a shot inside `chipRangeYds` (75) is auto-solved to REST at the pin (`solveChipEf` bisects `simShotRest`), so launch/spin changes there are distance-safe. Its SHAPE comes from `chipLoftDeg`→`chipLoftRef` (loft rising with length) + the `chipSpin`→`chipSpinRef`→`chipSpinPow` backspin ramp; its GROUND behaviour comes from `chipMu`. **Every chip in the band now releases** (2026-07-30): LW 15 yd carries 9.4 and runs 4.8 (1:0.51), 20 yd 12.7 + 7.4, 30 yd 21.5 + 7.7, 40 yd 35.7 + 3.6; SW 30 yd 16.7 + 14.1. Before this, LW 30 ran **0.2 yd** and LW 40 ran **−0.4**. Spin came down with it (40 yd 8319 → 5211 rpm) but that was for realism, not release — see `chipMu`. The 40 yd LW PITCH keeps 544ed1e's shape (launches ~43°, apexes ~30 ft, two hops); its apex fell 35→30 ft only because a shot that runs has to carry less to finish at the same pin, and the gate floor moved 30→26 ft for that reason. The gate asserts a **positive** release at every target (1.5 yd to 50 yd, 0.2 past 60 where the `chipMu` fade has mostly retired) and a ≥0.30 carry:roll for ≤20 yd — checking rest distance alone is exactly how "every chip rolls backwards" shipped unnoticed, since `solveChipEf` just flew the ball the whole way. The two-hop assertions are scoped to the LW: with `chipMu` in, a 30 yd SAND wedge is no longer a pitch at all — it carries 17, skips once and runs 12, which is what that club is for.
